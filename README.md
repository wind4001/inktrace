# InkTrace · 发票 / 小票手写手机号识别

> Read handwritten phone numbers and amounts off receipts — PaddleOCR + LLM.

从发票、小票的照片里，自动读出**手写手机号**、**实付金额**和**开票日期**。

针对的是 OCR 最难的那一类场景：手机号是**手写的**、写在票面空白处、字迹倾斜潦草，
而且整页扫描件缩放后小字容易漏检。光靠 OCR 引擎硬识别准确率很低，所以这里把
**PaddleOCR（检测+识别）** 和 **大语言模型（判别+纠错）** 组合起来用，并加了一层
**代码级的交叉校验**兜底。

支持三种用法：**Web 界面**（拖拽上传、多张并发）、**命令行**（单张）、**批量脚本**（整个文件夹）。

## 它识别什么

| 目标 | 说明 | 输出字段 |
|---|---|---|
| **手写手机号** | 票面上手写的 11 位手机号（重点） | `phone` |
| **实付金额** | 消费者最终实际支付的金额（已扣优惠券/优惠） | `amount` |
| **开票日期** | 小票开具/打印日期，统一 `YYYY-MM-DD` | `date` |

每一项都带一个 `*_needs_review` 布尔标记：**只要结果里含有任何推断成分，就标记为需人工复核**，
绝不静默地"猜一个看起来对的答案"给你。

## 工作原理

```
发票/小票图片
     │
     ▼
[1] 加载图片 ─────────── 兼容中文路径（cv2.imdecode 代替 cv2.imread）
     │
     ▼
[2] PaddleOCR 检测 ──── 全页检测 + 分块检测（1800px 分块、300px 重叠）后合并去重
     │                  分块是为了解决大图内部缩放导致的小号手写漏检
     ▼
[3] 文本行识别 ──────── 逐框透视矫正 → 放大 2x → 识别，得到「文本 + 坐标 + 置信度」
     │                  + 墨迹连通域查找：涂白印刷文字后，对残留墨迹聚类，
     │                    在区域尺度重新检测，捞出 OCR 漏掉的倾斜/潦草手写
     ▼
[4] LLM 判别 ───────── 把所有文本行（含归一化坐标、置信度、分区、手写候选标记）
     │                  整页交给大模型，让它判断哪一行是手写手机号
     │                  同时分别判别实付金额、开票日期
     │
     ├── 重叠行交叉核对 ── 纯代码逻辑：同一手写区域被检测成多个框时，
     │                    逐位对齐投票；冲突位用「同图模板匹配」裁决
     │                    （同一个人笔迹稳定，拿本图已确认位的字形做模板）
     │
     └── 二次精读 ─────── 初次结果不是完整合规手机号时，
                          对选中区域做 原图/灰度/CLAHE 三种增强再识别一遍，
                          连同初识结果交给 LLM 综合裁决
     ▼
[5] 输出 ────────────── 标注图（绿框=印刷体、橙框=手写候选、红框=判定结果）+ JSON
```

**为什么不直接让 LLM 看图？** 因为大模型读整页小票图里的手写数字，准确率并不比 OCR 高，
而且无法给出坐标证据。这里的分工是：OCR 负责"看见"，LLM 负责"判断和拼接"，
代码负责"校验"——三层各自做擅长的事，并且**每一层的结论都能被下一层反驳**。

**为什么要代码级交叉校验，而不全交给 LLM？** 实测 LLM 对"同一区域多个冲突读数"这类
信息采纳不稳定，同样的输入有时信 A 有时信 B。所以当多框投票 + 同图模板匹配给出**强证据**
（相关系数差 > 0.3）时，代码层直接改判并强制 `needs_review = true`，不依赖 LLM 的临场判断。

## 环境要求

- **Python >= 3.10**（依赖的最新版普遍要求 3.10+；在更旧的 Python 上 pip 可能只能解析到较旧版本）
- 一个**大模型的 API Key**（走 OpenAI 兼容协议，见[配置说明](#配置说明)）
- 纯 CPU 可跑。首次运行会下载 PaddleOCR 模型（几百 MB），耗时较长

## 快速开始

### 1. 安装依赖

```bash
# 建议用虚拟环境
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

### 2. 配置

```bash
# Windows
copy .env.example .env
# macOS / Linux
cp .env.example .env
```

编辑 `.env`，**至少填这三行**：

```ini
LLM_API_KEY=sk-你的Key
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-v4-flash
```

`LLM_MODEL` 是必填项——各家模型 id 不一样，代码里故意不写死默认值，
留空会直接报错并提示你去看 `.env.example` 里的服务商对照表。

> **这是唯一必须配置的东西。** `.env` 已被 `.gitignore` 排除，不会（也不应该）提交。

### 3. 跑起来

```bash
python app.py
```

浏览器打开 <http://127.0.0.1:5000>，把发票图片拖进去即可。

## 配置说明

### 大语言模型（必填）

本程序通过 **OpenAI 兼容协议**调用大模型，任何提供该协议的服务都能用。
改这三行即可切换服务商，**无需改代码**：

| 服务商 | `LLM_BASE_URL` | `LLM_MODEL` 示例 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-v4-flash`（便宜快速）/ `deepseek-v4-pro`（更强推理） |
| 通义千问（百炼） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| Kimi（Moonshot） | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| 本地 Ollama | `http://127.0.0.1:11434/v1` | `qwen2.5:14b`（`LLM_API_KEY` 随便填） |

> 表内 model id 为 2026-10 核实结果，各家可能调整，**以官方文档为准**。

⚠️ **对模型的唯一硬性要求**：需要较好的**指令遵循**和**JSON 输出**能力。
本程序的所有 LLM 交互都是"给一段文本行 → 只输出一个 JSON 对象"，
小参数量的本地模型可能输出格式不稳，此时换更大的模型即可。

### OCR 模型（可选，有默认值）

```ini
OCR_DET_MODEL=PP-OCRv6_medium_det
OCR_REC_MODEL=PP-OCRv6_medium_rec
```

默认用 PP-OCRv6 medium（34.5M 参数）。**如果你的环境拉不到 v6**，在 `.env` 里改成：

```ini
OCR_DET_MODEL=PP-OCRv5_server_det
OCR_REC_MODEL=PP-OCRv5_server_rec
```

> 代码里 `enable_mkldnn=False` 是为了绕开 **paddle 3.3.1** 的 oneDNN 路径在 v6 模型上的
> `ConvertPirAttribute2RuntimeAttribute` 报错。换 paddle 版本前请先单独跑一次
> `python -c "import recognize_phone as rp; rp.make_ocr()"` 验证。

## 三种使用方式

### 方式一：Web 界面（推荐，支持批量）

```bash
python app.py
```

- <http://127.0.0.1:5000>（**只监听本机回环地址**，不对局域网开放）
- 支持拖拽 / 点击选择 / **多张并发上传**，每张独立轮询进度
- 单张上限 80MB；支持 `.jpg .jpeg .png .bmp .webp .tif .tiff`
- 输出目录：`output/`，可通过 `/output/<文件名>` 直接访问

### 方式二：命令行（单张）

```bash
python recognize_phone.py 发票.jpg
python recognize_phone.py 发票.jpg --output 我的输出目录
python recognize_phone.py 发票.jpg --no-tiling     # 关闭分块检测（小图可加速）
```

### 方式三：批量脚本（整个文件夹）

```bash
python batch_run.py 图片目录 输出目录      # 推荐：显式传目录
python batch_run.py 图片目录               # 输出到 output/
```

⚠️ **不要直接跑 `python batch_run.py`。** 省略参数时它默认读 `test/`，
而 `test/` 在 `.gitignore` 里（那是放本地测试图片的目录），**全新 clone 后并不存在**，
会直接报 `文件夹不存在`。请把图片放进任意目录后显式传入，或自己先建一个 `test/` 目录。

只处理 `.jpg / .jpeg / .png`，不递归子目录，逐张打印结果并在最后汇总。

## 输出说明

每张图产出**两个文件**，放在输出目录：

| 文件 | 内容 |
|---|---|
| `<图名>_<哈希>_result.jpg` | 标注图。**绿框**=印刷体文本行，**橙框**=手写候选行，**红框**=最终判定为手机号的那一行，框上编号与 JSON 的 `line_index` 对应 |
| `<图名>_<哈希>.json` | 结构化结果 |

> 文件名里的 `<哈希>` 是**图片内容的短哈希**（10 位）。
> 加了它是因为：不同目录下的同名图片（如 `a/1.jpg` 与 `b/1.jpg`）如果只按文件名做键，
> 会共用同一份缓存，第二张图会**静默读到第一张的 OCR 结果**。内容相同的图片则有意复用缓存。

### JSON 字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `image` | str | 输入图片的路径（**可能是绝对路径**，含本机目录结构） |
| `phone` | str | 识别出的手机号（纯数字），识别不出为 `""` |
| `matches_regex` | bool | 是否符合 `^1[3-9]\d{9}$` |
| `needs_review` | bool | **是否需要人工复核**（含任何推断成分为 `true`） |
| `reason` | str | 判定理由（自然语言） |
| `line_index` | int | 命中的文本行号，对应标注图上的编号 |
| `ocr_text` | str | 该行的 OCR 原始文本 |
| `is_handwriting_candidate` | bool | 命中行是否来自墨迹分析的手写候选 |
| `amount` | str | 实付金额（如 `"123.45"`） |
| `amount_reason` | str | 金额判定理由 |
| `amount_needs_review` | bool | 金额是否需复核 |
| `amount_region_candidates` | list | 金额区域放大重读的候选文本（仅触发重读时存在） |
| `date` | str | 开票日期，`YYYY-MM-DD` |
| `date_reason` | str | 日期判定理由 |
| `date_needs_review` | bool | 日期是否需复核 |
| `cross_validated` | str | 触发重叠行交叉核对时的逐位投票说明（仅存在时输出） |
| `candidates` | list | 二次精读的各变体识别结果（仅触发时存在） |
| `chosen_box` | list | 选中区域的四角坐标（仅触发二次精读时存在） |
| `result_image` / `json_file` | str | 输出文件名 |

### 判读结果（Web 界面）

Web 界面按 `matches_regex` 和 `needs_review` 给出四种状态，**不会把不确定的结果伪装成确定**：

| 徽章 | 条件 | 含义 |
|---|---|---|
| 识别成功 | `matches_regex` 且非 `needs_review` | 可直接采用 |
| 格式合法 · 建议人工复核 | `matches_regex` 且 `needs_review` | 格式对，但经过推断（如片段拼接、模板匹配） |
| 部分识别 · 需人工复核 | 有 `phone` 但格式不合法 | 只读出部分数字，需对照标注图补全 |
| 未识别出 | `phone` 为空 | 未找到手写手机号 |

### 调用关系

```
    app.py                    batch_run.py          （CLI: recognize_phone.py 自身的 main）
      │                            │                            │
      └──────────────┬─────────────┴────────────────────────────┘
                     ▼
            recognize_phone.process_image()      ← 唯一的共用心智入口
             （加载 → OCR → 墨迹查找 → 交叉核对 → LLM 判别 → 输出）
```

三个入口（Web / 批量 / CLI）全部收敛到 `process_image()` 一个函数，
OCR 模型和 LLM 客户端都在入口处**初始化一次后复用**（所以首次启动慢，之后每张很快）。

> 用代码知识图谱扫下来，这个仓库是**干净的二分结构**：`app.py` 与 `recognize_phone.py`
> 分成两个社区，社区之间只有 1 条聚合调用边。也就是说 Web 层完全不掺和识别逻辑——
> `app.py` 总共只用到核心的三个函数（`make_ocr` / `make_llm` / `process_image`），
> 想换 Web 框架或加 CLI 子命令都不会碰到核心代码。

## 设计要点

几个不那么显然、但很关键的设计决定：

1. **分块检测（tiling）** —— 整页 OCR 会把大图缩放，票面顶部的小号手写数字很容易漏掉。
   所以除全页检测外，再用 1800px 分块（300px 重叠）扫一遍，按中心距离去重合并。

2. **墨迹连通域查找手写** —— 对常规检测整段漏掉的手写区域：先把已识别的印刷文字框
   涂白 → 对残留墨迹做连通域分析并按 x 轴聚类 → 对每个候选区域裁剪后
   **在区域尺度上重新检测**（避开整页缩放），只保留数字不少于 7 个的结果。

3. **重叠行交叉核对** —— 同一手写区域常被检测成 2–3 个重叠框。代码逐位对齐投票，
   **冲突位**用"同图模板匹配"裁决：同一个人笔迹稳定，用图中已确认位的字形当模板。
   只有相关系数差 > 0.3 的强证据才改判。

4. **绝不让 LLM 补全数字** —— 提示词里反复强调：读不全就如实输出部分数字并标
   `needs_review`，**不许推测缺失位**。所有涉及推断的结果都会被标记。

5. **金额的优先级规则** —— 实付金额 ≠ 票面大字。规则是：优先取"支付方式旁的金额"＞
   应付/合计减优惠券＞合计；**折扣不算抵扣**（合计已是折后价）。金额缺失或存疑时，
   会对标签行附近区域**放大重读**（整条放大 2x + 区域重新检测）后再综合判断。

6. **OCR 结果磁盘缓存** —— 整页 OCR 是主要耗时，结果缓存到
   `ocr_cache/`，调提示词或换 LLM 时不必重跑 OCR。缓存按**图片内容哈希**做键。

## 已知限制

- **异步任务只存在内存里**。`app.py` 的 `JOBS` 字典没有过期和上限，
  服务长时间运行会持续占用内存；重启服务后历史任务查询结果丢失。
  当前定位是**本机小批量工具**，不是常驻服务。
- **无并发上限**。同时上传很多张会让 CPU 上的 OCR 互相抢占，整体变慢。
- **手写识别无法保证 100%**。字迹潦草、连笔、被印章或折痕遮挡时可能只识别出部分数字，
  此时程序会明确标记 `needs_review` 并给出部分结果 —— **请务必人工核对**。
- **只针对中国大陆手机号**（`1[3-9]` 开头 11 位），不支持座机、国际号码。
- **仓库内没有示例图片** —— 发票是真实业务数据，含个人信息，不适合随仓库分发。
  请自备图片（或用 `tests/` 先验证环境是否装好）。
- `batch_run.py` 只扫描单层目录，不递归子文件夹。

## 隐私与数据

⚠️ **这一节请务必读一遍。**

本程序处理的是**发票和购物小票**，上面含有**真实姓名、手机号、消费记录**，属于个人信息。

- **所有处理都在本机完成**：图片不会上传到任何服务器。唯一的对外请求是
  **把 OCR 出的文本行发给大模型**做判别（这是本程序的设计前提，用云端模型时请注意这一点）。
  **如需完全离线，把 `LLM_BASE_URL` 指向本地 Ollama / vLLM 即可。**
- ⚠️ **上传的原图、识别结果、OCR 缓存会一直留在磁盘上**，没有任何自动清理：
  - `uploads/` —— 上传的原图
  - `output/` —— 标注图与 JSON 结果
  - `ocr_cache/` —— 整页 OCR 的全文（含识别出的手机号）
- 结果 JSON 里的 `image` 字段保存了**输入图片的路径**（可能是绝对路径），会一并暴露本机目录结构。
- 这些目录都已在 `.gitignore` 中，**不会**被提交。但处理完敏感票据后，请**手动删除**它们。
- Web 服务只监听 `127.0.0.1`，**不对局域网开放，也没有登录认证**——请勿改成 `0.0.0.0` 后
  直接暴露到公网。

## 常见问题

**Q: 启动很慢 / 卡在"加载 PaddleOCR 模型与 LLM 客户端"**
正常。首次启动要下载并加载模型（几百 MB），之后复用。模型会缓存到本地的
`.paddle/` / `.paddlex/` 目录。

**Q: 报 `请在 .env 中配置 LLM_MODEL`**
`.env` 里 `LLM_MODEL` 是空的。各家模型 id 不同，必须显式填写，
参考 `.env.example` 里的服务商对照表。

**Q: 报 400 / model not found**
`LLM_MODEL` 的名字和 `LLM_BASE_URL` 对不上，或该服务商已改过 model id。
模型名的写法**以你所用服务商的官方文档为准**。

**Q: OCR 报 `ConvertPirAttribute2RuntimeAttribute`**
paddle 版本与 PP-OCRv6 模型不兼容。要么用 `paddlepaddle==3.3.1`（见 `requirements.txt`），
要么在 `.env` 里把 OCR 模型换成 PP-OCRv5 server。

**Q: 想重复调提示词，不想每次都等 OCR**
不用管——OCR 结果已自动缓存到 `ocr_cache/`，第二次跑同一张图会直接读缓存。
缓存按图片内容哈希命名，改图才会失效。

**Q: 结果不对，想看看是哪一行被选中了**
打开 `output/` 里的标注图：**红框**就是程序判定的那一行，框上编号对应 JSON 的 `line_index`。
橙框表示该行来自墨迹分析（手写候选）。
